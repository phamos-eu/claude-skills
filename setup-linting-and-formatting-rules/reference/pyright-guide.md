# Phamos static type checker

Pyright is the type checker used in the phamos standard. Unlike Ruff and ESLint (which blocks commits), Pyright runs in advisory mode. It surfaces type errors in your editor as you write code and can be run manually, but it does not fail CI. The goal is to catch bugs during development, not to create merge blockers.

Topics covered here:

1. `export_python_type_annotations` hook
2. Doctype field annotations and `TYPE_CHECKING`
3. Annotating function parameters and return values
4. Typing `frappe.get_doc` and similar APIs with `cast()`
5. Typing `frappe.db.get_value` and similar APIs
6. Prefer explicit `None` handling over `cast()`
7. `TYPE_CHECKING` guard for Doctype imports
8. Avoid overusing `cast()`
9. Type checking does not replace runtime validation
10. AI-generated type workarounds to avoid

### 1. `export_python_type_annotations` hook

This hook, available since Frappe v15, tells Frappe to auto-generate type annotations for your Doctype fields whenever a Doctype is created or updated. Without it, Pyright has no way to know what fields exist on `self` inside your controller, and it will report `Unknown` for every field access.

Set this in your app's `hooks.py`:

```python
## hooks.py

export_python_type_annotations = True

```

Once enabled, the next time you save a Doctype in the browser, Frappe regenerates the controller file and injects a block like this at the top of the class:

```python
## my_app/my_app/doctype/maintenance_contract/maintenance_contract.py

class MaintenanceContract(Document):
    # begin: auto-generated types
    # This code is auto-generated. Do not modify anything in this block.

    from typing import TYPE_CHECKING

    if TYPE_CHECKING:
        from frappe.types import DF

        customer: DF.Link
        annual_amount: DF.Currency
        start_date: DF.Date
        status: DF.Select
    # end: auto-generated types

    def validate(self):
        ...

```

Do not edit anything inside the `# begin: auto-generated types` / `# end: auto-generated types` block. It gets overwritten on every Doctype update.

### 2. Doctype field annotations and `TYPE_CHECKING`

Once `export_python_type_annotations` is enabled and a Doctype has been saved, the auto-generated block gives Pyright the field types it needs. You can immediately get field-level type checking in all controller methods.

The `TYPE_CHECKING` guard means these imports only exist at type-check time, not at runtime. This avoids import overhead and circular import issues.

```python
## before — no annotations, Pyright reports Unknown for all field accesses

class MaintenanceContract(Document):
    def validate(self):
        total = self.annual_amount * 12   # annual_amount is Unknown, no type safety
        self.full_name = self.first_name + self.last_name  # no error caught here

```

```python
## after — annotations generated by the hook, Pyright now knows the field types

class MaintenanceContract(Document):
    # begin: auto-generated types
    if TYPE_CHECKING:
        from frappe.types import DF
        customer: DF.Link
        annual_amount: DF.Currency
        start_date: DF.Date
    # end: auto-generated types

    def validate(self):
        total = self.annual_amount * 12   # Pyright confirms annual_amount is a number type
        # if you wrote self.annual_amount + "monthly", Pyright flags it as a type error

```

### 3. Annotating function parameters and return values

Doctype field annotations cover `self`, but standalone functions and helper methods also benefit from annotations. Adding parameter and return type hints lets Pyright catch mismatches at the call site, not only inside the function body.

```python
## before — no annotations, caller gets no type safety

def get_customer_label(customer_name, suffix):
    return customer_name + " " + suffix

result = get_customer_label(123, "GmbH")   # Pyright cannot warn that 123 is wrong

```

```python
## after — annotated, caller gets an error if they pass the wrong type

def get_customer_label(customer_name: str, suffix: str) -> str:
    return customer_name + " " + suffix

result = get_customer_label(123, "GmbH")
## Pyright flags: Argument of type "int" cannot be assigned to parameter of type "str"

```

A practical Frappe example:

```python
## before

def apply_annual_increase(doc, rate):
    doc.annual_amount = doc.annual_amount * (1 + rate)

```

```python
## after

from my_app.my_app.doctype.maintenance_contract.maintenance_contract import MaintenanceContract

def apply_annual_increase(doc: MaintenanceContract, rate: float) -> None:
    doc.annual_amount = doc.annual_amount * (1 + rate)

```

### 4. Typing `frappe.get_doc` with `cast()`

`frappe.get_doc` returns `Document`, the base Frappe type. This means Pyright does not know about any of your custom fields or methods on the returned object. Use `cast()` to tell Pyright what the actual type is.

`cast()` is a runtime no-op. It only instructs Pyright. It does not change the actual object.

```python
## before — return type is Document, Pyright reports Unknown for custom fields

doc = frappe.get_doc("Maintenance Contract", self.contract)
doc.annual_amount = 1200   # Pyright: Cannot access attribute "annual_amount" on Document

```

```python
## after — cast tells Pyright the actual type

from typing import cast
from my_app.my_app.doctype.maintenance_contract.maintenance_contract import MaintenanceContract

doc = cast(MaintenanceContract, frappe.get_doc("Maintenance Contract", self.contract))
doc.annual_amount = 1200   # Pyright now knows annual_amount exists and its type

```

The same pattern applies to `frappe.get_cached_doc` and `frappe.new_doc`:

```python
from typing import cast
from my_app.my_app.doctype.job_application.job_application import JobApplication

new_doc = cast(JobApplication, frappe.new_doc("Job Application"))
new_doc.applicant_name = "Robera"   # Pyright resolves this correctly

```

### 5. Typing `frappe.db.get_value`

`frappe.db.get_value` returns `Unknown`. Pyright cannot infer the type of a database lookup. You can handle this in two ways: `cast()` when you are confident the value exists, or explicit `None` handling when the value may be absent (see topic 6).

```python
## before — country is Unknown, any operation on it is untyped

country_name = frappe.db.get_value("Country", {"name": self.country}, "name")
label = "Country: " + country_name   # Pyright: Unknown + str is untyped

```

```python
## after using cast() — appropriate only when you are certain the value exists

from typing import cast

country_name = cast(str, frappe.db.get_value("Country", {"name": self.country}, "name"))
label = "Country: " + country_name   # Pyright now treats country_name as str

```

The same applies to `frappe.db.get_single_value` and `frappe.get_all`:

```python
from typing import cast

default_currency = cast(str, frappe.db.get_single_value("Global Defaults", "default_currency"))

```

### 6. Prefer explicit `None` handling over `cast()`

`frappe.db.get_value` returns `None` when no matching record is found. Casting to `str` in that case silences Pyright but does not prevent a runtime crash when you try to use the value. Explicit `None` checks are safer and also narrow the type automatically, so Pyright no longer needs a `cast()`.

```python
## before — cast hides the possibility that the value is None

from typing import cast

tax_template = cast(str, frappe.db.get_value("Customer", self.customer, "default_tax_template"))
frappe.db.set_value("Sales Invoice", self.name, "taxes_and_charges", tax_template)
## if no Customer record exists, tax_template is None at runtime, and this crashes silently

```

```python
## after — None check first, then Pyright knows the value is str from that point on

tax_template = frappe.db.get_value("Customer", self.customer, "default_tax_template")

if tax_template is None:
    frappe.throw("No default tax template found for customer {0}".format(self.customer))

## Pyright now knows tax_template is not None below this line
frappe.db.set_value("Sales Invoice", self.name, "taxes_and_charges", tax_template)

```

Use `cast()` for `db.get_value` only when you have already validated that the record exists through another path, such as a `validate` method or a prior query that guarantees the result.

### 7. `TYPE_CHECKING` guard for Doctype imports

When you import a Doctype class only to use it as a type annotation (for example, in a function parameter), wrap the import in a `TYPE_CHECKING` guard. This prevents the import from running at runtime, which avoids circular imports and unnecessary overhead.

```python
## before — the import runs at runtime even though it is only needed for annotations

from my_app.my_app.doctype.maintenance_contract.maintenance_contract import MaintenanceContract

def apply_increase(doc: MaintenanceContract, rate: float) -> None:
    doc.annual_amount = doc.annual_amount * (1 + rate)
## this can cause a circular import if maintenance_contract.py imports from this module

```

```python
## after — the import is guarded and only visible to Pyright, not to Python at runtime

from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from my_app.my_app.doctype.maintenance_contract.maintenance_contract import MaintenanceContract

def apply_increase(doc: "MaintenanceContract", rate: float) -> None:
    doc.annual_amount = doc.annual_amount * (1 + rate)
## note the string literal "MaintenanceContract" — required because the class is not
## imported at runtime, so the bare name would raise a NameError

```

If you are on Python 3.10+ and have `from __future__ import annotations` at the top of the file, you can drop the string literal and write `doc: MaintenanceContract` directly, because all annotations are evaluated lazily.

```python
from __future__ import annotations
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from my_app.my_app.doctype.maintenance_contract.maintenance_contract import MaintenanceContract

def apply_increase(doc: MaintenanceContract, rate: float) -> None:
    doc.annual_amount = doc.annual_amount * (1 + rate)

```

### 8. Avoid overusing `cast()`

`cast()` should only be used when you know something that Pyright genuinely cannot infer, such as the specific Doctype returned by `frappe.get_doc`. It should never be used to silence a legitimate type error that points to a real problem in your logic.

```python
## bad — cast is used to silence a real type mismatch, not to inform Pyright

from typing import cast

def get_invoice_total(doc):
    return cast(float, doc.grand_total + doc.shipping_amount)
## if grand_total is DF.Currency and shipping_amount is unknown, the cast hides the issue

```

```python
## good — the types are handled correctly instead of silenced

def get_invoice_total(doc: SalesInvoice) -> float:
    return float(doc.grand_total) + float(doc.shipping_amount)
## explicit conversion is safer and the intent is clear

```

A useful rule of thumb: every `cast()` in your code should have a comment explaining why it is safe. If you cannot write that explanation, the `cast()` probably should not be there.

```python
## acceptable cast with a clear reason

from typing import cast

## frappe.get_doc returns Document, but we know this is always a SalesInvoice
## because this function is only called from the SalesInvoice controller
doc = cast(SalesInvoice, frappe.get_doc("Sales Invoice", self.invoice))

```

### 9. Type checking does not replace runtime validation

Pyright catches type errors at development time, but it only sees the types you declare. A value that passes type checking can still violate business rules at runtime. Type annotations are not constraints on actual values.

```python
## this passes Pyright with no errors

class MaintenanceContract(Document):
    if TYPE_CHECKING:
        from frappe.types import DF
        annual_amount: DF.Currency
        contract_years: DF.Int

    def validate(self):
        contract_years: int = 999999   # valid int, Pyright is fine with this
        # but 999999 years is not a valid business value

```

```python
## runtime validation still required alongside type annotations

def validate(self):
    if self.contract_years <= 0 or self.contract_years > 10:
        frappe.throw("Contract years must be between 1 and 10")

    if not self.customer:
        frappe.throw("Customer is required")

```

Type annotations describe the shape of data. DocType validations, field constraints, and explicit checks enforce the meaning of data. Both are needed.

### 10. AI-generated type workarounds to avoid

AI coding tools (including Cursor and Claude) will sometimes produce code that makes Pyright happy without actually improving your code. The most common pattern to watch for is using `getattr()` to bypass a Pyright error on a controller field.

```python
## bad — AI-generated workaround, bypasses Pyright rather than fixing the root cause

class SalesInvoice(Document):
    def validate(self):
        customer = getattr(self, "customer", None)   # Pyright stops complaining, but why?
        if customer:
            ...

```

```python
## good — the field is properly annotated, Pyright resolves it correctly

class SalesInvoice(Document):
    # begin: auto-generated types
    if TYPE_CHECKING:
        from frappe.types import DF
        customer: DF.Link
    # end: auto-generated types

    def validate(self):
        if self.customer:   # Pyright knows self.customer exists and its type
            ...

```

The `getattr(self, "field", None)` pattern is sometimes correct, for example when accessing a field that may not exist on all versions of a Doctype, or when writing truly generic code that operates on arbitrary documents. But if it is there only because Pyright was complaining and you wanted it to stop, fix the annotation instead.

When reviewing AI-generated code, check every `getattr`, every `cast`, and every `# type: ignore` comment. Each one should have a clear reason. If it does not, it is likely a workaround that hides a real type issue.

### Setup

#### Install Pyright

```bash
pip install pyright

```

Or with npm if you prefer the Node-based version (same tool, slightly faster updates):

```bash
npm install -g pyright

```

#### `pyrightconfig.json`

Place this file at the root of your app, for example `apps/phamos/pyrightconfig.json`:

```json
{
  "include": ["phamos"],
  "exclude": ["**/__pycache__"],
  "pythonVersion": "3.11",
  "typeCheckingMode": "basic",
  "reportMissingImports": false,
  "reportMissingModuleSource": false
}

```

Replace `"phamos"` with the app folder name if working on a different app, for example `"hanses_app"`, `"becharged"`, or `"kefiya"`.

`typeCheckingMode: "basic"` is the recommended starting point for a Frappe project. It surfaces real issues without requiring full annotation coverage across all files.

`reportMissingImports` and `reportMissingModuleSource` are set to `false` because Frappe and ERPNext ship without type stubs, so Pyright would otherwise report errors on every `import frappe` line.

#### Run on the whole app

Run from inside the app root, for example `apps/phamos/`:

```bash
cd apps/phamos
pyright

```

Pyright picks up `pyrightconfig.json` automatically when you run it from the same directory. No path argument needed.

If you are outside the app directory, pass the path explicitly:

```bash
pyright apps/phamos/phamos/

```

#### Run on a single file

To check one file before committing or fixing, pass the file path directly:

```bash
pyright apps/phamos/phamos/phamos/doctype/maintenance_contract/maintenance_contract.py

```

This is useful for checking your changes in isolation without seeing errors from the rest of the app. Pyright still reads `pyrightconfig.json` for settings, but only reports on the file you passed.

#### Editor integration

In VS Code, install the **Pylance** extension. Pylance uses Pyright internally and shows type errors inline as you type. No extra configuration is needed beyond the `pyrightconfig.json` above.
